# Excess report notifications or pending acceptance

Scope: this local lab's queues only. PostgreSQL accepted rows are authoritative. Do not flush Redis, clear the live queue, delete guards, reset reports or overwrite the database to make a graph healthy. Preserve terminal failures, deadline misses and diagnostic evidence.

Inspect the infrastructure panels for ready/reserved/delayed notifications and actual queued/suppressed/error dispatch outcomes. Suppression means a waiting notification owner exists; it does not prove completion or readiness. Redis depth and durable pending counts differ: native reservations, timing and legacy/expired duplicate deliveries can contribute. IDs belong in logs, not metric labels. Correlate report.accepted, report.processing and notification.transport_failed by report_id, then inspect API status and stored attempt/result.

Check worker replicas/readiness, scheduler heartbeat and dependency failures first. The unchanged five-second SQL dispatch reservation retries absent transport state. Native reserved notifications expire after twenty seconds; a pre-handle max-attempt failure releases only the matching guard and reconciliation publishes again. A business attempt begins only after SQL claim. Transport failure is visible in lab_notification_failures_total and structured logs; it does not silently consume a business attempt or make the report completed.

For a stuck pending record, distinguish an actual waiting/reserved notification from an orphaned guard. Whole queue/guard state loss has a tested recovery contract; selective corruption has a different limit. The twenty-four-hour guard expiry is only metadata safety and cannot establish a sixty-second completion promise. Request-specific inspection must validate the synthetic report UUID and remain bounded; do not export raw queue payloads or authorization values. Native bulk/delayed publication deduplication and Redis Cluster are outside this implementation.

Stop only a bounded load generator, allow workers to drain and confirm both accepted business records and all three queue states before another confirmation. Do not regard completed records as proof that stale notifications are gone. Native liveness can stay healthy with stuck useful work; use readiness, pending/overdue outcomes and queue progress separately. Late results never repair missed deadlines.

Reproduction commands: make g4-pause (thirty-second worker pause), make g4-preclaim (one ephemeral consumer SIGKILL before handle), make g4-interruption (two correlated active workers), make g4-load (bounded scheduled arrivals/confirmation). Do not run them together or interrupt pause restoration. Each saves sanitized evidence and restores affected replicas; no live Redis deletion is required. Isolated transport-state deletion tests run only through make test in Redis database 15 with uniquely owned synthetic queue keys. Restore/check make smoke and python3 scripts/observability-check.py after recovery.

See docs/g4/queue-protocol.md, ADR 013, docs/g4/validation.md and docs/status.md. A rollback must first quiesce the project queue, then restore the native driver/configuration via a source deployment without resetting PostgreSQL. Returning to the old driver also restores its measured publication amplification; old guard metadata expires and must not be confused with business state.
