# Provisional SLOs and measurement contract
These are portfolio lab assumptions over a rolling 30-day window, not production commitments or achieved results. 99.9% availability is a useful conventional service target; 500ms supports prompt acknowledgement/status lookup; 60s gives asynchronous work reasonable completion room. No discovered customer requirement supports these values yet. A short lab run tests mechanics only. Review targets after measured demand and recovery behavior.

## API availability (99.9%)
Outcome: a valid authenticated report submission/status lookup gets a successful response. Eligible population is requests reaching the instrumented `POST /api/reports` or `GET /api/reports/{id}` application routes, classified `normal`, resulting in 2xx or 5xx. Authentication, validation, missing report, idempotency conflict and other 4xx are excluded (caller errors); health, metrics, unrelated routes, intentional faults and load-test traffic are excluded. Duplicate valid submissions are eligible HTTP events but create only one accepted report. No 3xx is expected.
Numerator: eligible 2xx responses. Denominator: eligible 2xx + 5xx. Middleware records route template/status class and server processing time; atomic shared PostgreSQL counters across all API processes/replicas are scraped once by exporter. `sum(rate(...[30d]))` ratios are request-weighted; intended budget = 0.001 × eligible count, consumed = eligible 5xx count, remaining = budget - consumed. No client timeout/connection refusal/edge-network instrumentation exists: those events are outside this application-observed population and client-load errors must be reported separately. Thus this is not complete user-perceived network availability.

## API latency (99% within 500ms)
Outcome: prompt response to an eligible request. Same eligible population/exclusions as availability (including server failures: availability independently evaluates success). Numerator: histogram bucket `le="0.5"`; denominator: histogram count; misses = count - bucket. Same middleware/exporter aggregation, summed across route/status and normal traffic. Budget = 0.01 × count. Measurement starts in global middleware and ends before durable telemetry writes, response serialization/transmission, client connection or queue completion. The metric-write overhead is outside the measured interval; k6/client timings include it and are the authoritative experiment latency. Document this gap when interpreting thresholds.

## Processing timeliness (99% completed within 60s)
Outcome: a durably accepted unique report has a stored completed result by accepted_at+60s. Population: ALL unique accepted normal reports whose deadline lies in `(now-30d, now]`, regardless of current state. Exclude duplicate submissions, uncommitted/rejected requests, load and fault reports. A cohort enters the denominator at its deadline, not at completion. Numerator: completed_at <= deadline_at; denominator: every report in that deadline cohort. Pending, processing and failed reports at expired deadlines count as misses. Late completion never changes a miss into success; completed_at is immutable once terminal, and a late timestamp remains > deadline. Scheduler persists immutable deadline_met flags/counters for audit, but exporter independently queries the source-of-truth deadline cohorts, so a stopped scheduler cannot hide overdue misses. Short-window burn ratios use identical deadline-cohort queries (5m,30m,1h,2h,6h,1d,3d), not completed-job histograms. A report moves out of a window only when its deadline ages out. Budget = 0.01 × cohort size; consumed = cohort size - met; remaining = budget - consumed.

`lab_processing_seconds` histogram contains completed jobs ONLY and is diagnostic, never this SLI. Deadline sampling has scrape-resolution delay; queue waiting + service retries contribute to elapsed acceptance/completion. Retain accepted records at least the SLO horizon; this lab has no cleanup job. PostgreSQL index supports deadline selection; query/metric contention is a capacity limitation.

## Missing telemetry, zero traffic and history
Zero traffic/cohort size has no observed reliability outcome. Ratios are represented as zero misses for arithmetic/alert stability; they never imply 100% compliance. Dashboards must be read alongside counts and target health. Missing exporter/series or stale scheduler heartbeat is UNKNOWN and raises TelemetryUnavailable, not an assumed success. Business metrics commit with transitions; HTTP metric-write loss is logged, but no independent counter recovers missing HTTP events. Database/network telemetry outages invalidate positive compliance claims. No available API history for a full 30d means UNESTABLISHED, even if a partial-history `:30d` query returns a value. Exporter process success cannot prove all request instrumentation succeeded. Counter resets require explicit data-reset audit; no reset executed under G1.

## Rules, alert derivation and routing
Definitions are Git provisioned in observability/rules.yml. Burn rate = miss ratio / allowed miss fraction. For a 720-hour window, a burn rate B sustained for W hours consumes `B × W / 720` of the error budget. Thresholds: 14.4 over 1h (2% budget) with 5m confirmation; 6 over 6h (5%) with 30m; 3 over 1d (10%) with 2h; 1 over 3d (10%) with 6h. Each condition requires both windows, exporter up and a 2m pending period. First two severities critical; slower two warning. These are event-weighted budget approximations when traffic varies; actual consumed budget uses eligible counts, not wall time alone. Low cohort counts can yield noisy processing burns; no arbitrary minimum event count suppresses real misses. Revisit thresholds with demand.

Routing is local-console only: Prometheus `/alerts` and Grafana alert panel, no email/Slack/pager, no Alertmanager notification claim. Operator checks severity, eligible traffic volume, telemetry, and runbooks. `LabDemoProcessingMiss` separately uses fault cohorts over 5m, pending15s, severity info and mode=accelerated-demonstration. It proves rule evaluation/visible recovery; it is NEVER a 30-day burn-rate result. Deterministic promtool tests simulate full intended windows for long-window correctness without pretending simulated traffic was real.
