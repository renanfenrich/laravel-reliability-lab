# Repeatable equivalent load generator
scripts/experiments.py uses Python stdlib ThreadPoolExecutor + urllib, scheduled constant-rate arrivals and generated unique idempotency keys. It is the selected k6-equivalent to avoid another binary/runtime dependency. 128 concurrent client threads, 15s request timeout, request samples and scheduling lateness are captured. Workload is synthetic, authenticated POST; DB records establish completion independently of HTTP 202. Client errors/timeouts count as errors; never filtered. Rates 2,10,30,60,120,240 rps are bounded exploratory steps (20s each), not a claimed capacity target. Stop at first observed saturation: >1% client errors, <99% <=500ms client latency or <99% expired reports completed <=60s. Wait up to95s for deadline cohorts; unfinished jobs are misses. Not reaching saturation within these bounds means capacity remains unestablished, not unlimited.

Each step includes a cooldown/cohort observation interval: this is burst response, not hours of steady state. Do not extrapolate short bursts to sustained production capacity. If generator arrival lateness is large, flag generator limits before attributing saturation to service. Loopback port-forward selects one API pod rather than balancing both API replicas; worker pool remains both replicas. Kubernetes service balancing and external networking capacity remain untested. Raw samples identify this limitation. Optional future k6 can broaden workload without changing event population.
