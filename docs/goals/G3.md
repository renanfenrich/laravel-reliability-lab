# G3 — overload resilience and bottleneck attribution

Status: **planned; implementation not authorized**. The owner requested this plan on 2026-10-11. G2 publication and merge authorization does not authorize G3 execution or publication. Start implementation only after a separate explicit request, reviewing G2 integration and current repository instructions first.

## Evidence and purpose

G2 established two passing ten-minute runs at 30 requests/s in this workstation configuration. The latest run accepted 18,000 reports with no HTTP errors and every processing deadline met. The 60 requests/s step failed: 917 HTTP errors, client p99 9.417 seconds, 53.18% processing timeliness, probe-driven API restarts, and generator p99 delay 8.211 seconds. These are local observations, not a precise server-only capacity ceiling. See [the latest report](../g2/load-rerun-20261011.md) and [original capacity evidence](../g2/capacity.md).

G3 will identify the dominant constraint and make overload behavior explicit and recoverable while preserving committed acceptance, idempotency, dispatch recovery, and visible terminal failures. It does not promise that 60 requests/s will pass, invent a new capacity target, or establish a rolling 30-day SLO.

## A — baseline and probe contracts

Inspect documented state, Git status, host resources, configuration and active project services. Do not rerun discovery or recreate the cluster without a reason. Capture a source/configuration fingerprint and replay the established load protocol with isolated cohorts and no overlapping fault tests.

Correlate request latency, FPM occupancy, probe events, restarts and queue growth. Separate process liveness from readiness and useful progress: a busy but responsive process must not be repeatedly killed merely because the shared HTTP request pool is saturated. A genuinely stopped process must still be detected and recovered. Keep dependency checks bounded in readiness, and use existing scheduler/cohort telemetry for progress. Validate startup, graceful termination, healthy overload and actual process failure with meaningful tests; do not simply increase every timeout or hide readiness failures.

Kubernetes distinguishes [startup, readiness and liveness probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/). PHP supports [an independent FPM status listener](https://www.php.net/manual/en/install.fpm.configuration.php), which can inform a minimal internal diagnostic design. Verify the chosen probe path independently of a saturated application pool; keep status endpoints private and retain nonroot/container restrictions.

## B — bounded bottleneck measurement

Use existing Prometheus, Grafana, Loki and project collectors before adding services. Measure per-container CPU, throttling, memory, FPM pool occupancy, gateway/FastCGI waiting, PostgreSQL transaction/lock pressure, queue depth, retry behavior and scheduler/reconciliation delay where available. Explicitly identify missing measurements instead of substituting zeros.

If database evidence requires normalized query statistics, evaluate [PostgreSQL 18 pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html), including preload/restart requirements and collection overhead. Protect the live lab database with the existing private backup procedure before an authorized database restart/configuration change. Record version compatibility, bounded overhead and rollback steps; never collect raw credentials or personal data. Labels must remain bounded; correlation IDs belong in structured logs.

The phase report must distinguish observations, hypotheses and unknowns, with timestamps linking errors to resource and probe behavior. A generator-limited run cannot establish a precise application ceiling. Distributed tracing is deferred unless these measurements demonstrate a specific gap that requires a separately scoped decision; a new tracing stack is not a G3 requirement.

## C — minimal measured change and acceptance contract

Select a change only from measured evidence: for example a query/index, transaction critical section, worker/reconciliation batch or FPM/gateway configuration. Compare one change at a time against the same workload. Preserve all G1/G2 reliability invariants and retained observability history.

If bounded admission is necessary, document the limit, measurement basis and response contract before implementing it. Admission must occur before durable acceptance: explicit overload rejection uses the chosen 429 or 503 contract with Retry-After; a successful acceptance still corresponds to a committed PostgreSQL record. Do not automatically replay POST requests at the gateway. A client whose acknowledgement is lost must recover through the same idempotency key. Accepted jobs cannot be dropped to shorten the queue.

Eligible overload rejections count as unsuccessful API outcomes; do not change SLI eligibility or traffic labels to conceal failures. Only committed acceptances enter processing cohorts, and failed/unfinished reports remain misses after their immutable deadlines. Separate normal, load and intentional fault evidence using the existing policy.

## D — repeatable comparisons and recovery

Use the G2 scheduled-arrival protocol: bounded 180-second steps at 10, 30 and 60 requests/s, stopping on saturation or generator/resource limits, followed by a 600-second confirmation at an observed passing rate. These are experimental inputs, not capacity promises. Keep the prior 30 requests/s result as a regression comparison; explain any deviation rather than forcing a passing threshold. Record identical or explicitly changed resources, data volume, simulator behavior, background activity and source/configuration fingerprints.

Capture throughput, HTTP status ratios, client/server latency, arrival delay, replica distribution, every expired processing cohort, unfinished work, resource histories and probe/restart events. Measure backlog drain and return to readiness after bounded overload. Compare the same configuration before/after the selected change. If generator limits prevent attribution, record that limitation and evaluate a project-local independent generator before making stronger capacity claims.

Acceptance requires evidence that overload behavior is bounded and observable, committed reports recover without duplicate results, and healthy process liveness does not create avoidable restart cascades. Actual process termination must still recover. Record remaining errors, deadline misses and memory risks; no requirement says the 60 requests/s workload must succeed.

## E — validation and deliverables

Run meaningful application tests for any changed acceptance/probe behavior and preserve validation/authentication, idempotency, dispatch recovery, retry exhaustion, duplicate delivery and interruption coverage. Run rule fixtures, Terraform checks, strict manifest validation, image configuration checks, Kubernetes smoke and the existing seven-target/55-query observability audit. Update CI for changed contracts, distinguishing local results from hosted runs for an exact SHA. No numerical count is a substitute for the required behavior.

Deliver docs/g3/validation.md, a measured capacity comparison, diagnostic/probe decisions, overload and recovery runbook updates, and one blameless incident report only after an executed experiment. Store reproducible sanitized evidence under evidence/g3/ with UTC timestamps, command outputs, SHA, versions, resources and limitations. Keep private dumps and secrets ignored. Update docs/status.md after each phase, listing failed and unexecuted checks. Commit independently reviewable phases using Conventional Commits; stop READY FOR HUMAN REVIEW without publication until separately authorized, retaining owner authorization for publication and merge.
